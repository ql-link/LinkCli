# LinkCli 架构与运行契约

## 模块职责

- `src/registry`：标准 MCP 工具发现、不可变服务版本、风险分类、人工审核、可信项目免审、探活和项目状态。
- `src/gateway`：平台凭据、统一工具清单、工具路由、项目 Token 装配、标准 MCP 服务端和错误映射。
- `src/collection`：生成轮次标识，脱敏、截断调用摘要，并通过有界队列异步投递 L2。
- `src/analysis`：消费 L2 已结算的完整 Query，按定时批次完成模块路径提取、宽口径聚类、组内场景统计、覆盖缺口识别和 L4 候选 Outbox 写入。
- `src/db`：MySQL 物理模型、事务和查询；`schema.sql` 是绿地数据库真值源。
- `src/auth`：控制台账号、Argon2id 密码和 7 天滑动服务端会话。
- `src/console`：面向 React 控制台的同域查询、权限、差异视图和写操作接口。
- `web`：React + Vite 控制台，生产产物由 Express 同域托管。

## 权限边界

管理接口先校验部署级 `x-admin-api-key`，再读取可信代理提供的平台用户与角色。项目负责人只能登记和修改自己的项目，审核人不能审核自己提交的版本，只有运营者可以永久下线项目。

浏览器不调用 `/admin`，也不保存部署级管理密钥。控制台通过 `/api` 使用 HttpOnly、SameSite Cookie；注册只创建普通成员，项目负责人由项目所有者字段判断，审核员和运营管理员由运营管理员授予。所有写请求校验同源，最终权限始终由服务端执行。

服务绑定到 `0.0.0.0` 或 `::` 时必须配置 `MCP_ALLOWED_HOSTS`，由 MCP HTTP 入口校验 Host 头，避免 DNS rebinding。

外部 Agent 使用平台凭据访问 `/mcp`。第一阶段不配置项目级或工具级授权，因此所有有效平台凭据获得相同的可用工具清单。网关解密项目 Token 后，仅把它作为下游 MCP 认证信息发送；平台凭据、终端用户身份、用户原始问题和内部路由字段不会进入下游业务参数。项目内部数据权限由项目 MCP 决定。

## 发布与健康

首次登记和每次变更都会生成不可变候选版本。默认进入人工审核；可信项目免审开关默认关闭。批准只代表版本获得发布资格，首次探活成功后才原子切换生效版本。输入输出结构删除或变化被视为高风险，对应工具在审核期间暂停；其他工具继续服务。

草稿阶段的提交时间为空；进入待审核或免审批准时写入 `submitted_at`。七天审核滞留只按该时间计算，不使用草稿创建时间近似。

项目健康状态只持久化 `unknown`、`healthy`、`unhealthy` 和最近探活时间。连续成功、失败计数只保存在当前进程；多实例部署需要保证同一项目的探活归属稳定，或者后续把瞬时计数迁移到共享协调组件。健康结论过期后，项目工具不会继续出现在清单中。

## 调用与采集

公开工具名为 `<projectKey>__<originalName>`。网关在工具定义中加入必填参数 `__linkcli_user_question`，调用前将它从业务参数剥离。每次调用只向下游发送一次，第一阶段不自动重试。调用完成后按平台身份、会话和调用次序生成轮次标识，并异步投递脱敏摘要；L2 不可用不会改变业务响应。

## L3 定时 Query 分析

L3 不消费单次 `CallEnvelope`，也不在用户请求期间实时聚类。它只处理 L2 写入 `mcp_analysis_input` 的完整已结算轮次；输入必须包含稳定 `turn_id`、结算版本、Query、不可逆用户摘要，以及实际 Project、Module、Tool、参数键和结果。零调用或未命中 MCP 的 Query 也必须由 L2 显式写入，否则 L3 无法发现这类需求。

同一 `turn_id` 在批处理前到达更高结算版本时，旧版本被标记为已取代且不参与聚类；轮次已经分析后不接受静默改版，调用方必须发起显式补偿重建，避免旧成员、场景和频次残留在类别中。

调度器默认每 5 分钟读取最多 1000 条未分析输入，并使用 MySQL advisory lock 避免多个 LinkCli 实例同时执行批次。正常输入按有序 `Project/Module` 组合限定候选范围，再使用本地确定性相似度归类；查询、修改、删除等 Tool 动作只形成组内场景，不作为 Query 类别硬边界。没有完整 Module 路径的输入进入未覆盖需求池，L3 不根据 Tool 名猜测 Module。单条输入失败时只回滚该输入并继续批次，失败记录保留到下一批重试。

候选门槛由 `L3_*` 环境变量配置。没有尝试现有 Skill 且质量达标的类别产生 `new_skill`，明确存在覆盖缺口的类别产生 `expand_skill`，零调用类别产生 `uncovered_demand`。候选与类别状态在同一事务写入 `mcp_l4_candidate_outbox`；同一类别的同类候选只交付一次，但 `new_skill` 交付后仍可因后续覆盖缺口产生一次 `expand_skill`。L3 不生成 Skill、不调用业务 MCP，也不主动查询权威业务数据库；回放和数据库反向校验属于 L4。

空库通过 `npm run db:init` 创建全部表；已有数据库在启用调度器前运行 `npm run db:upgrade:analysis`。升级脚本只从 `src/db/schema.sql` 的 L3 标记位置读取并使用 `CREATE TABLE IF NOT EXISTS`，不维护第二份 DDL。

## 已知运行限制

- 进程内清单和健康计数不提供跨实例强一致性，数据库生效指针仍是发布真值源。
- `L2_ENDPOINT` 未配置时使用空投递器，适合第一阶段独立验证 L1，但不会产生真实采集数据。
- 当前网关仍只产生调用级 `CallEnvelope`；在 L2 接入完整轮次写入契约前，L3 调度器可以运行但不会获得可分析输入。L3 明确不会从零散调用猜测轮次边界或 Module。
- 首版 Query 相似度是本地确定性字符特征算法，阈值需要通过影子运行样本持续校准；不调用外部 LLM。
- `L4_EVENT_ENDPOINT` 未配置时，暂停、恢复、发布、探活失败和七天滞留事件只改变平台状态，不会通知外部 Skill 或运营系统。
- `db:init` 只创建空库，没有面向已有数据库的升级迁移链。
- 当前没有 Web 管理控制台，运营通过受保护的 REST API 完成。
